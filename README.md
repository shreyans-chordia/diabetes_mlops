# Diabetes MLOps Pipeline

An end-to-end MLOps pipeline that trains a diabetes prediction model, tracks every experiment, versions the data, and serves predictions through a containerized REST API.

> Educational project built on the Pima Indians Diabetes dataset. Predictions are **not** medical advice.

## Tech stack

| Area | Tool |
|---|---|
| Modeling | Python, scikit-learn |
| Experiment tracking | MLflow |
| Data versioning | DVC |
| Serving | FastAPI + uvicorn |
| Packaging | Docker |
| Testing | pytest |

## Project structure

```
diabetes-mlops/
├── src/
│   ├── app.py              # FastAPI app (/predict, /health)
│   ├── train.py            # Trains and compares models, exports the winner
│   └── download_data.py    # Downloads the dataset and adds column headers
├── tests/                  # pytest suite (API, config, data)
├── data/
│   └── diabetes.csv.dvc    # DVC pointer file (the raw CSV is not in Git)
├── params.yaml   
├── dvc.yaml                # DVC pipeline definition (train stage)
├── dvc.lock                # Exact hashes of the last pipeline run
├── metrics.json            # Metrics written by training, tracked by DVC              # All training settings and model hyperparameters
├── tasks.bat               # Short commands: train, test, serve, docker-build...
├── requirements.txt        # Runtime dependencies (used by Docker)
├── requirements-dev.txt    # Runtime + test dependencies
├── pytest.ini
├── Dockerfile
├── model/                  # Generated by training, git-ignored, served by the API
└── mlflow.db, mlruns/      # Generated MLflow tracking data, git-ignored
```

## Setup (Windows, Command Prompt)

Run every command from the project root.

1. Create and activate a virtual environment:
   ```
   python -m venv venv
   venv\Scripts\activate
   ```
2. Install dependencies. DVC is a dev tool, so it is not in either requirements file:
   ```
   python -m pip install -r requirements-dev.txt dvc
   ```
3. Download the dataset:
   ```
   mkdir data
   python src/download_data.py
   ```
   `data/diabetes.csv` is tracked by DVC and excluded from Git. No DVC remote is configured yet, so `dvc pull` does not work until one is added.

## Task runner

`tasks.bat` wraps the common commands and always uses the virtual environment's Python.

| Command | What it does |
|---|---|
| `tasks train` | Train and compare models, export the winner to `model/` |
| `tasks test` | Run the pytest suite |
| `tasks serve` | Start the API locally on port 8000 with auto-reload |
| `tasks mlflow-ui` | Open the MLflow UI on port 5001 |
| `tasks docker-build` | Build the `diabetes-api` image |
| `tasks docker-run` | Run the container on port 8000 |

In PowerShell, type `.\tasks <command>` instead.

## Configuration

All training settings live in `params.yaml`: the dataset path and split, the imputation toggle, the metric used to pick the winner, the export folder, and each model's hyperparameters. Change a value there and re-run `tasks train`; no code edits needed.

- `selection.metric` accepts `accuracy`, `precision`, `recall` or `f1`.
- `data.use_imputation` (default `false`) replaces impossible zeros in Glucose, BloodPressure, SkinThickness, Insulin and BMI with train-set medians, so runs with and without imputation can be compared.
- Models listed under `models:` are all trained. Supported names are `random_forest` and `gradient_boosting`.

## Train and compare models

```
tasks train
```

Both candidates are trained as separate MLflow runs, compared on the held-out test set, and only the winner is exported to `model/`.

| Model | Accuracy | Precision | Recall | F1 |
|---|---|---|---|---|
| Random Forest | 0.766 | 0.686 | 0.636 | **0.660** |
| Gradient Boosting | 0.740 | 0.627 | **0.673** | 0.649 |

- The winner is picked by test F1. Random Forest won in the latest run.
- The F1 gap is small. With a test set of about 154 rows it is within noise, so cross-validation is planned before treating the ranking as reliable.
- Gradient Boosting has the higher recall, which matters for screening-style use. Set `selection.metric: recall` in `params.yaml` to select on it instead.
- Each run logs a `use_imputation` param, four `test_*` metrics, and a `selected_for_serving` tag.

### Explore runs in the MLflow UI

```
tasks mlflow-ui
```

Open http://127.0.0.1:5001 and select the `diabetes-prediction` experiment. Port 5001 is used because 5000 can conflict with other local servers.

## Reproducible pipeline (DVC)

Training is defined as a DVC stage in `dvc.yaml`. It depends on `src/train.py`, the dataset and the settings in `params.yaml`, and it produces `model/` and `metrics.json`. `dvc.lock` records the exact hashes of the last run.

| Command | What it does |
|---|---|
| `dvc repro` | Re-runs training only if the code, data or params changed |
| `dvc metrics show` | Prints the metrics from `metrics.json` |
| `dvc push` | Uploads the dataset and model to the DVC remote |
| `dvc pull` | Downloads the dataset and model from the DVC remote |
| `dvc status -c` | Checks that the local cache and the remote are in sync |

To rebuild everything from a fresh clone:

```
git clone https://github.com/shreyans-chordia/diabetes_mlops
cd diabetes_mlops
dvc pull
```

The remote is currently a local folder (`D:\dvc-remote`, set in `.dvc/config`), so `dvc pull` only works on the machine that holds it. It will be replaced with a cloud remote before CI/CD is added.

## Run the tests

```
tasks test
```

The suite has 12 tests covering the API endpoints (including rejection of bad input), the `params.yaml` configuration, and the dataset shape. API tests need `model/` and data tests need `data/diabetes.csv`; a test is skipped, not failed, when its file is missing. Run `tasks train` first to create `model/`.

## Run the API locally

```
tasks serve
```

The API loads the trained model from `model/`, so run `tasks train` first.

### Endpoints

**`GET /health`**
```
curl.exe http://127.0.0.1:8000/health
```
Returns `{"status":"healthy","model_source":"model"}`.

**`POST /predict`**
```
curl.exe -X POST http://127.0.0.1:8000/predict -H "Content-Type: application/json" -d "{\"Pregnancies\": 6, \"Glucose\": 148, \"BloodPressure\": 72, \"SkinThickness\": 35, \"Insulin\": 0, \"BMI\": 33.6, \"DiabetesPedigreeFunction\": 0.627, \"Age\": 50}"
```
Returns `prediction` (0 or 1), `probability`, and `status` (`diabetic` or `healthy`). The sample above returns `prediction: 1`, `probability` of about 0.69, and `status: diabetic`.

Interactive docs are available at http://127.0.0.1:8000/docs.

## Run with Docker

Make sure Docker Desktop is running, and re-run `tasks train` whenever you want the image to contain a newer model.

```
tasks docker-build
tasks docker-run
```

The image is based on `python:3.11-slim` and contains `src/`, the pinned runtime dependencies, and the exported `model/` folder. The same `curl.exe` commands above work against the container.

## Design decision: model export instead of artifact lookup

MLflow 3.x resolves relative artifact paths to absolute paths when an experiment is created. On Windows these become absolute Windows paths, which do not exist inside a Linux container. To avoid this, training exports the selected model to a fixed `model/` folder with `mlflow.sklearn.save_model()`, and the API loads it directly. Serving no longer depends on MLflow's tracking store.
