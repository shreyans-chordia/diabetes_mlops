# Diabetes MLOps Pipeline

An end-to-end MLOps pipeline that trains a diabetes prediction model, tracks every experiment, versions the data, and serves predictions through a containerized REST API.

> Educational project built on the Pima Indians Diabetes dataset. Predictions are **not** medical advice.

## Tech stack

| Area | Tool |
|---|---|
| Modeling | Python, scikit-learn |
| Experiment tracking | MLflow |
| Data versioning | DVC |
| Serving | FastAPI + uvicorn |
| Packaging | Docker |

## Project structure

```
diabetes-mlops/
├── app.py                 # FastAPI app (/predict, /health)
├── train.py               # Trains and compares models, exports the winner
├── download_data.py       # Downloads the dataset and adds column headers
├── requirements.txt       # Runtime dependencies (used by Docker)
├── Dockerfile
├── data/
│   └── diabetes.csv.dvc   # DVC pointer file (the raw CSV is not in Git)
├── model/                 # Generated by train.py, git-ignored, served by the API
└── mlflow.db              # Generated MLflow tracking store, git-ignored
```

## Setup (Windows, Command Prompt)

1. Create and activate a virtual environment:
```
   python -m venv venv
   venv\Scripts\activate
```
2. Install dependencies (DVC is a dev tool, so it is not in `requirements.txt`):
```
   python -m pip install -r requirements.txt dvc
```
3. Download the dataset:
```
   mkdir data
   python download_data.py
```
   The `data/diabetes.csv` file is tracked by DVC and excluded from Git. A DVC remote is not configured yet, so `dvc pull` will not work until one is added.

## Train and compare models

```
python train.py
```

`train.py` trains two candidates as separate MLflow runs, compares them on the held-out test set, and exports only the winner to `model/`.

| Model | Accuracy | Precision | Recall | F1 |
|---|---|---|---|---|
| Random Forest | 0.766 | 0.686 | 0.636 | **0.660** |
| Gradient Boosting | 0.740 | 0.627 | **0.673** | 0.649 |

- The winner is selected by test F1 (`SELECTION_METRIC` in `train.py`). Random Forest won in the latest run.
- The F1 gap is small. With a test set of about 154 rows it is within noise, so cross-validation is planned before treating the ranking as reliable.
- Gradient Boosting has the higher recall, which matters for screening-style use. Set `SELECTION_METRIC = "recall"` to select on it instead.
- `USE_IMPUTATION` (default `False`) replaces impossible zero values in Glucose, BloodPressure, SkinThickness, Insulin and BMI with train-set medians, so runs with and without imputation can be compared.
- Each run logs a `use_imputation` param, four `test_*` metrics, and a `selected_for_serving` tag.

### Explore runs in the MLflow UI

```
mlflow ui --port 5001 --backend-store-uri sqlite:///mlflow.db
```

Open http://127.0.0.1:5001 and select the `diabetes-prediction` experiment. Port 5001 is used because 5000 can conflict with other local servers.

## Run the API locally

```
python -m uvicorn app:app --reload
```

The API loads the trained model from the `model/` folder. Run `train.py` first, since `model/` is not stored in Git.

### Endpoints

**`GET /health`**
```
curl.exe http://127.0.0.1:8000/health
```
Returns `{"status":"healthy","model_source":"model"}`.

**`POST /predict`**
```
curl.exe -X POST http://127.0.0.1:8000/predict -H "Content-Type: application/json" -d "{\"Pregnancies\": 6, \"Glucose\": 148, \"BloodPressure\": 72, \"SkinThickness\": 35, \"Insulin\": 0, \"BMI\": 33.6, \"DiabetesPedigreeFunction\": 0.627, \"Age\": 50}"
```
Returns `prediction` (0 or 1), `probability`, and `status` (`diabetic` or `healthy`). The sample above returns `prediction: 1`, `probability` of about 0.69, and `status: diabetic`.

Interactive docs are available at http://127.0.0.1:8000/docs.

## Run with Docker

Make sure Docker Desktop is running, and re-run `train.py` first whenever you want the image to contain a newer model.

```
docker build -t diabetes-api .
docker run -p 8000:8000 diabetes-api
```

The image is based on `python:3.11-slim` and contains `app.py`, the pinned dependencies, and the exported `model/` folder. The same `curl.exe` commands above work against the container.

## Design decision: model export instead of artifact lookup

MLflow 3.x resolves relative artifact paths to absolute paths when an experiment is created. On Windows these become absolute Windows paths, which do not exist inside a Linux container. To avoid this, `train.py` exports the selected model to a fixed `model/` folder with `mlflow.sklearn.save_model()`, and `app.py` loads it directly. Serving no longer depends on MLflow's tracking store.
